# Benchmarks

**English** | [Português](BENCHMARKS.pt-BR.md)

The same service, written by a coding agent from the same prompt, with and without java-skills, and then hand-tuned under a profiler to find what the skills were missing. Measured under load in containers sized like an AWS t4g.micro, 3 times per scenario. October 2026.

## What was measured

- **The service:** `orders-api`, the specification used by [go-skills' benchmark](https://github.com/rafapeixer/go-skills/blob/main/benchmarks/orders-api/SPEC.md): create and read orders with items in PostgreSQL, a paginated list per customer, and a quote that calls a pricing service that is "usually ~20 ms, sometimes much slower". 8 replicas share an 80-connection database budget.
- **The prompt:** [`benchmarks/orders-api/generate/`](benchmarks/orders-api/generate/orders-api/prompt.md), Java 25 and Spring Boot 4.1 with virtual threads, JDBC and HikariCP. The agent also writes the Dockerfile, because the heap, the GC and the container user are part of what the skills teach.
- **The harness:** go-skills' [`harness/`](https://github.com/rafapeixer/go-skills/tree/main/benchmarks/orders-api/harness). Every container is limited to 2 vCPU and 1 GiB, a contract test must pass before any load, and every run starts from a fresh, seeded database. Each number is the median of 3 runs; the full tables have the range.
- **The versions** ([`benchmarks/orders-api/impl/`](benchmarks/orders-api/impl/)):

| Version | How it was made |
|---|---|
| Java without skills | Generated by the agent with no plugin |
| Java with java-skills v1 | Generated with the first release of the skills |
| Java hand-tuned | v1 tuned by hand with JFR, one measured change at a time ([TUNING.md](benchmarks/orders-api/TUNING.md)) |
| Java with java-skills v2 | Generated after the tuning lessons went into the skills |
| **Java with java-skills v3** | Generated after the v2 regression was fixed in the skills; now the [reference service](reference/orders-api/) |

## What it shows

- **Without the skills, the service falls over and stays down.** Above capacity it queues every request: 96.5% errors at 4,000 req/s, 4.6 s median latency, and 28% errors after the load has already dropped back.
- **The first skills fixed the failure mode but not the cost.** v1 rejected the excess at once and recovered, but used more CPU per request than the version without skills, and its pool of 5 connections (sized for a 100% deploy surge) became the queue.
- **Hand-tuning found what was missing.** One statement per read instead of a transaction with two queries, one statement to create an order with its items, a virtual-thread executor for the JDK `HttpClient`, the pool sized from Kubernetes' real 25% surge, a fixed G1 heap and a larger Tomcat accept queue cut CPU per request by 45% and moved the warm capacity from 0 to 5,000 req/s. Every change, with its JFR evidence, is in [TUNING.md](benchmarks/orders-api/TUNING.md).
- **v2 regressed, and the regression became a rule.** With the lessons in the skills the agent got the CPU right, but the `http-server` skill said to bound concurrency per dependency instead of the thread pool. With virtual threads nothing else caps requests in flight, so at 4,000 req/s the heap filled and the JVM died with `OutOfMemoryError`. The skill now requires an in-flight cap at the edge.
- **v3, generated from the skills alone, matches the hand-tuned service.** Same warm capacity (5,000 req/s), the same 0% errors at 5,000, more consistent under overload (1.5–1.7% errors across runs, against 0–18.8% for the hand-tuned one), and 43% less memory. It falls short of the hand-tuned version only at 6,000 req/s, where the 2 vCPU run out.

## Cost: 10,000 req/s for a month

Same model as go-skills: each instance planned at 70% of its measured warm capacity, at least 2 instances, T4g in unlimited mode (hourly price plus US$ 0.04 per vCPU-hour above the baseline), 730 hours. Database: RDS PostgreSQL db.t4g.micro Single-AZ with 20 GB gp3. Every Java version's peak memory fits a t4g.micro except v2.

With java-skills v3 the Java fleet costs **37% less in EC2** than the version without skills, and **25% less including the database**. Go with go-skills, from [go-skills' benchmark](https://github.com/rafapeixer/go-skills/blob/main/BENCHMARKS.md), stays cheaper: Java's ceiling on 2 vCPU is CPU, near 6,000 req/s at about 0.35 ms per request.

## Limits

- One host runs the load generator and every container; containers are CPU- and memory-limited, the host is x86 Docker Desktop, not Graviton.
- One generation per version: another run of the agent writes different code. The 11-task eval in the [README](README.md) measures the skills across 10 runs per task.
- The ramps stop at 3,000 req/s (cold) and 8,000 req/s (warm), so capacities above those were not measured.
- The cost model uses list prices from October 2026 and excludes the load balancer and data transfer, which are the same for every version.
- Seven of the 18 runs of "Java without skills" failed to start (a DNS failure while building the image): one each in capacity, 8 replicas and overload, two each in slow dependency and high load. Those medians use the 2 or 1 runs that completed; the warm-JVM scenario has all 3.
